## Чем задание отличается от лекции

В лекции создан обычный `POST /api/chat`. В этом проекте он **уже полностью работает** вместе с валидацией, обработкой ошибок и Spring AI. Повторно собирать контроллер/transport не нужно.

Новая задача — отдельный `POST /api/explanations`, позволяющий пользователю выбрать способ объяснения: BRIEF или GUIDED. Скопированный код lecture не реализует этот контракт и не проходит новые acceptance-тесты.

Предоставлены DTO, endpoint, вызов ChatClient и безопасная обработка ошибок. Реализуйте только [ExplanationPolicy.messages](src/main/java/dev/myfrei/repopilot/explanation/ExplanationPolicy.java). Это явный TODO; базовый чат от него не зависит.

## Пользовательский сценарий

```http
POST /api/explanations
Content-Type: application/json

{"message":"Чем record отличается от класса?","mode":"GUIDED"}
```

Успех: `{"answer":"..."}`. Режим GUIDED просит пошаговое объяснение, BRIEF — краткое. Если mode не указан, применяется BRIEF; неизвестное значение — HTTP 400 до вызова сервиса.

## Контракт политики

1. Отклонить null/blank message, исходную длину больше 4000 Java char и null mode через IllegalArgumentException.
2. Удалить пробелы по краям вопроса через strip(). Остальной текст, включая фигурные скобки и команды в вопросе, не переписывать.
3. Вернуть неизменяемый список ровно из двух сообщений: SystemMessage и UserMessage.
4. SystemMessage содержит общую роль помощника Java-разработчика и выбранный формат. Для BRIEF инструкция содержит `3 предложения`, для GUIDED — `5 шагов`.
5. Пользовательский текст находится только в UserMessage. Он не должен заменять/переписывать выбранную system-инструкцию.
6. Не возвращать константный ответ: готовый ExplanationService передаёт эти сообщения в настоящий ChatClient.

Это управление инструкцией, не валидатор фактического числа предложений модели. Успешный unit-тест не доказывает послушание реальной LLM.

## Проверки

Из этой папки с JDK 25:

```bash
./mvnw -DskipTests package
./mvnw -Dtest=ExplanationAcceptanceTest,ExplanationHttpAcceptanceTest test
./mvnw test
```

В `src/test/java/.../chat` сохранены regression-тесты готовой лекционной базы. В `.../explanation` добавлены отдельные проверки новой политики и endpoint: режимы, роли, неизменность вопроса, границы, enum/DTO validation и реальный ChatClient поверх mock ChatModel. Они не требуют весов Ollama.

Каркас собирается. Новые поведенческие проверки сначала красные, базовые — зелёные. Приёмка — весь набор без пропусков, изменения условий тестов и подстановки ответа вместо LLM.

## Ручной эксперимент

После реализации запустите Ollama по лекции и приложение. Отправьте один вопрос обоими режимами в новых запросах:

```bash
curl -sS http://127.0.0.1:8080/api/explanations -H 'Content-Type: application/json' -d '{"message":"Что такое record?","mode":"BRIEF"}'
curl -sS http://127.0.0.1:8080/api/explanations -H 'Content-Type: application/json' -d '{"message":"Что такое record?","mode":"GUIDED"}'
```

Сравните полезность формата, а не только длину. Найдите пример, где модель нарушила инструкцию, и опишите наблюдение. Не заявляйте проверенное поведение, если реальный inference не выполнялся.
