## Проверка запакованного приложения, Web и REPL

Запущен настоящий executable Boot JAR на отдельном порту с копией учебного workspace. Вызовы Ollama обрабатывала управляемая HTTP-фикстура; это проверка интеграции, не качества реальных весов.

1. Через настоящую страницу `agent.html` создана job; пока ответ модели удерживался, интерфейс показывал `RUNNING` и события.
2. Отключение обновлений и перезагрузка URL с `sessionId` подключили страницу к той же job. Счётчик вызовов модели остался равен одному: нового запуска не было.
3. После ответа модели выполнены `startPlanStep → readFile → completePlanStep`; план стал `COMPLETED`, run — `FINAL_ANSWER`. Проверка кода осталась явно неподтверждённой.
4. Строка `<img src=x onerror="alert(1)">` отобразилась обычным текстом. UI использует `textContent`.
5. Запущен настоящий Java `SessionRepl` из собранного JAR через Boot `PropertiesLauncher`. `/attach`, `/status`, `/plan`, `/skills`, `/events` получили те же состояние и события через реальный `HttpClient`. Дополнительных вызовов модели не было. Также проверена публичная команда `exec:java` из лекции.
6. Во второй Web-задаче на ожидании ответа модели отправлена отмена. После возврата ответа получены `STOPPED/CANCELLED`; `TOOL_STARTED` отсутствуют. Отмена кооперативная: она не обещает мгновенно прервать сетевой вызов.

Итого 4 HTTP-вызова фикстуры: 3 у завершённого исследования и 1 у отменённого. Все запущенные для проверки процессы остановлены.

Unit/integration tests дополнительно проверяют закрытый JSON, идемпотентность отправки и конфликт тела, лимиты jobs/waiters, replay gap, отмену до привязки run, отсутствие чужой привязки, порядок блокировок и поздние ответы прежнего подключения.

## Проверка ДЗ через настоящие HTTP endpoints

Отдельно запущены JAR каркаса и закрытого контрольного варианта. В каждом созданы две остановленные jobs одного диалога и два `PENDING` запроса проверки. Модель для этого сценария недоступна: jobs честно остановились без model/tool calls.

- Каркас возвращает HTTP 501 / `ATTENTION_NOT_IMPLEMENTED`.
- Контрольный вариант показывает два pending approval перед двумя остановками; общие approval refs не дублируются.
- Ack скрывает остановки, но сохраняет pending approvals.
- `maxItems=1` сообщает `omittedBlockingCount=1` и `allActionableVisible=false`.
- Поддельный статус и ack будущей позиции отвергаются с HTTP 400.
- Отдельное ручное `REJECT` убирает соответствующий pending approval из следующего обзора.
- Сам inbox не запускает jobs и проверки: число jobs остаётся 2, reports остаются пустыми.

## Границы результата

ДЗ развивает проект новым обзором нескольких задач, а не повторяет event coordinator или REPL. Подтверждение просмотра не разрешает операции.

Состояние хранится в памяти процесса. Перезапуск сервера не восстанавливает jobs. Лента событий ограничена, поэтому gap требует загрузки snapshot. Это локальный учебный интерфейс без многопользовательской аутентификации. Токеновый streaming модели и транспорт событий job — разные вещи. Реальные локальные веса и темп прохождения требуют пилота; шаблон [эксперимента](lecture/evaluation/Interfaces-Experiment.md) оставлен незаполненным.
