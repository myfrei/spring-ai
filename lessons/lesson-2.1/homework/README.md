## Чем задача отличается от лекции

Лекция берёт свежий непрерывный хвост истории. ДЗ добавляет выбор важных старых пар внутри доступного memory snapshot: они должны пережить удаление свежего хвоста по бюджету.

В homework **уже включено готовое базовое приложение lecture**. Реализовывать его заново или переносить ответы из лекции не требуется. Новый учебный код находится в `dev.myfrei.repopilot.homework`; незаполнен только метод нового класса `PinnedContextAssembler`. REST-включение и остальная инфраструктура предоставлены.

| Что дано | Что нужно добавить |
| --- | --- |
| Весь работающий срез лекции и его регрессионные тесты | Новую policy, которой в лекции нет |
| Новый API, DTO и вызов policy в продукте | Самостоятельный алгоритм по контракту ниже |
| 5 отдельных acceptance-проверок | Собственное объяснение выбранного поведения и его ограничений |

## Запуск проверок

Из этой папки, с JDK 25:

```bash
./mvnw -DskipTests package
./mvnw -Dtest='*Test,!*HomeworkAcceptanceTest' test
npm ci
npm test
./mvnw -Dtest=PinnedContextHomeworkAcceptanceTest test
```

Каркас собирается. Базовые Java/JS-проверки должны быть зелёными; последние 5 acceptance сначала красные из-за явного TODO. После реализации запустите полный `./mvnw test` и `npm test`.

Не подменяйте реализацию константами и не отключайте тесты. После выполнения задания должны пройти базовые и новые приёмочные проверки.

## Контракт закрепления

Реализуйте `PinnedContextAssembler.assemble`. `pinnedPairs` — индексы полных user/assistant-пар в переданном history snapshot, начиная с нуля. Это не ID строки SQLite и не бессрочная память. Если старая пара уже не вошла в окно ConversationMemoryFactory, этот endpoint не загружает её из архивной истории.

1. Проверьте чётность истории и чередование USER/ASSISTANT. Отклоняйте null, отрицательные, выходящие за границы и повторные pin-индексы.
2. Получите обязательные system/current-user/документы через готовый baseline assembler с пустой историей. Не меняйте FULL_CONTEXT и его правило обязательного корпуса.
3. Сначала выберите все закреплённые пары. Если они с обязательным контекстом не помещаются, верните `ConversationProblem/PINNED_CONTEXT_TOO_LARGE`. Не снимайте закрепление молча.
4. Затем добавляйте самые свежие незакреплённые пары. При первой не помещающейся паре остановитесь.
5. Итоговые пары идут в хронологическом порядке, независимо от порядка pin-индексов. Нельзя раздвоить обмен, продублировать pin или изменить входной список.
6. В ContextReport правильно укажите estimatedInputTokens, included/omittedHistoryTurns, сохранив provenance и параметры исходного обязательного плана.

Готовый helper `messages` собирает хронологический prompt. Это алгоритм приоритета, а не новое хранилище памяти. Вызов второго memory advisor после него нарушил бы бюджет.

## Проверка через API

Запустите приложение и создайте несколько коротких обменов обычным чат-API. В актуальном окне памяти pair index 0 — самый ранний из доступных, а не обязательно первый за всё время диалога. Подставьте реальный UUID:

```bash
curl -sS http://127.0.0.1:8080/api/conversations/CONVERSATION_UUID/context/pinned/preview \
  -H 'Content-Type: application/json' \
  -d '{"message":"Какой важный факт мы обсудили?","mode":"CHAT","pinnedPairs":[0]}'
curl -N http://127.0.0.1:8080/api/conversations/CONVERSATION_UUID/context/pinned/stream \
  -H 'Content-Type: application/json' \
  -d '{"message":"Какой важный факт мы обсудили?","mode":"CHAT","pinnedPairs":[0]}'
```

Эти endpoints добавлены для ДЗ; обычные маршруты из лекции сохраняются. Сравните один и тот же snapshot с pins=[] и pins=[0]. Отдельно проверьте pin, который сам больше inputBudget: модель не должна получать усечённую важную пару.

## Что сдать

Исходник policy, результаты регрессий/acceptance и [SUBMISSION.md](SUBMISSION.md). Объясните, почему pin не разрешает превысить контекст и почему persistent pins по ID SQLite потребовали бы отдельного дизайна. Бланк обычного CHAT/FULL_CONTEXT-сравнения остаётся дополнительным, не подменяет проверку закрепления.

Усложнение: спроектировать устойчивые pin IDs для полных завершённых turn, не путая их с индексом текущего memory snapshot.
