  -Dtaskshelf.http.jar="$PWD/task-http-server/target/taskshelf-mcp-http-server-0.0.1-SNAPSHOT.jar"

`CircuitGatewayIT` сам запускает свой сервер на свободном порту, останавливает его, проверяет три сбоя/OPEN/no-IO, запускает заново и подтверждает свежую SDK-сессию после probe. Время cooldown задаёт тестовый Clock. Он не останавливает уже запущенный вами сервер; Docker и Ollama этому отдельному тесту не нужны. Профиль `circuit-it` включайте после решения TODO.

Сначала запустите HTTP-сервер и подготовьте RepoPilot/RAG по лекции. Для приложения включите `--repopilot.mcp-host.enabled=true`. ДЗ добавляет только:

```http
POST /api/mcp/resilient/workflow
Content-Type: application/json

{"taskId":"TASK-101","question":"Какие документы помогут проверить исправление?"}
```

Исходные `/api/mcp/workflow` и `/api/mcp/model` остаются базовыми. Новый маршрут передаёт тот же запрос в `McpHostEngine.withGateway(...)`: меняется граница доступности удалённого чтения, вся валидация и обработка RAG сохраняются. При пропуске из-за открытого circuit ответ содержит `MCP_CIRCUIT_OPEN`, а `remoteCalls=0`; модель и embeddings в этом запросе не вызываются.

## Машина состояний

Конфигурация provided bean: threshold3, cooldown30s, один экземпляр на данный удалённый сервис. В тестах время задаёт `Clock`; никаких sleep, фоновых задач или реальных 30-секундных ожиданий не нужно.

| Состояние | acquire | complete |
|---|---|---|
| CLOSED | Выдать разрешение с уникальным id | HEALTHY сбрасывает последовательные сбои; TRANSPORT_FAILURE увеличивает их; threshold открывает circuit |
| OPEN до retryAt | Отказать без вызова delegate | Старые/отклонённые разрешения ничего не меняют |
| OPEN при now >= retryAt | Выдать ровно одну HALF_OPEN probe | Пока probe не завершена, остальные запросы получают отказ |
| HALF_OPEN | Новые запросы отклоняются | HEALTHY → CLOSED; TRANSPORT_FAILURE → OPEN с новым cooldown от времени **завершения** probe |

`HEALTHY` обозначает отсутствие транспортного сбоя. Это не утверждение, что пользовательская задача выполнена. Provided adapter относит к TRANSPORT_FAILURE только `GatewayException.Kind.AVAILABILITY`. Авторизация, protocol/validation и business tool errors передаются вызывающему коду без подмены, но не открывают circuit как сетевую аварию. Устранение неправильного токена всё равно требуется.

Поля `Permit(id,generation,allowed,state,retryAfterMs)` и `Snapshot(state,failures,retryAt,probeInFlight)` уже объявлены. Используйте предоставленные state/inFlight/generation/clock поля либо эквивалентное внутреннее представление, сохранив API.

Требования:

1. CLOSED допускает параллельные обращения; каждый разрешённый permit получает отдельный id. Счётчик относится к последовательности **завершений**: HEALTHY сбрасывает его, новый транспортный сбой начинает отсчёт заново.
2. При threshold перейти в OPEN, установить retryAt=clock.instant()+cooldown. Обновление состояния атомарно.
3. OPEN не допускает вызов до срока; retryAfterMs положительный и отражает оставшееся ожидание. На точной границе допускается одна probe. Откат часов не даёт раннего пропуска.
4. Одновременно может выполняться только одна HALF_OPEN probe. Все остальные отклоняются, включая конкурентные вызовы. Пока probe выполняется, retryAfterMs может быть0: время её завершения неизвестно.
5. После успеха probe сбросить failures, probeInFlight и retryAt, перейти в CLOSED. После сбоя начать новый cooldown от момента complete.
6. Разрешение одноразовое. Повторный complete, отклонённый permit и завершение из старого поколения игнорируются. В частности, давно начатый запрос не может закрыть уже OPEN circuit или испортить состояние после успешного восстановления.
7. Состояние не должно пересекаться между экземплярами для разных сервисов. Сохраняйте thread safety. Не добавляйте автоматические повторы, scheduler, fallback-ответ или persistence.
8. Параметры конструктора проверяются готовым кодом: threshold1..10, cooldown>0 и <=5min, clock обязателен. Внешние аргументы пользователя не выбирают сервер, токен или policy.

Для счётчиков transport attempts не придумывайте успешные RPC: отказ gate происходит до delegate. У gateway настоящие ошибки transport/session сбрасывают cached client для следующего запроса; тот же провалившийся запрос автоматически не повторяется. Поэтому HALF_OPEN может установить новую сессию после перезапуска сервера.

## Сценарий проверки

1. Доступный сервер: новый маршрут читает задачу и проходит тот же RAG, что workflow лекции.
2. Остановите только свой MCP-процесс. Три запроса получают транспортную ошибку; после третьего circuit OPEN.
3. Следующий запрос сразу даёт MCP_CIRCUIT_OPEN и ноль удалённых вызовов. Это ожидаемая ошибка доступности, а не NO_EVIDENCE и не успешный ответ модели.
4. Запустите сервер снова. До retryAt запроса к нему нет. После cooldown допускается одна probe; при успешном чтении circuit CLOSED. Если индекс ещё не опубликован, host вернёт INDEX_NOT_READY. Если опубликованный индекс не дал подходящих документов, возможен NO_EVIDENCE. Оба результата независимы от восстановления MCP: circuit оценивает только удалённое чтение задачи.
5. Повторите unit-сценарий с бизнес-ошибкой и покажите, что ошибка не скрылась за фиктивным ответом и не открыла circuit.

Восемь acceptance проверяют порог/сброс, точную границу времени, успешную и неудачную probe, одноразовые permits и поздние завершения, конкурентную probe, изоляцию экземпляров/clock rollback и валидацию конфигурации. Три provided adapter-теста проверяют отсутствие IO при отказе, классификацию всех gateway kinds и отсутствие retry/подмены результата.
