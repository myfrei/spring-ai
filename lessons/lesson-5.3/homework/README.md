# Домашнее задание 5.3. Проверка готовности пакета изменений

[Материалы урока](../README.md) · [Лекция](../lecture/README.md) · [Приёмочные тесты](src/test/java/dev/myfrei/repopilot/batch/ProposalBatchPolicyAcceptanceTest.java) · [Отчёт по ДЗ](SUBMISSION.md)

В [лекции](../lecture/README.md) RepoPilot предлагает одну точечную правку, показывает её человеку и применяет только после отдельного решения. В этом задании вы добавляете другую возможность: **предварительную проверку нескольких предложений как одного списка**.

Пользователь хочет заранее увидеть, что один файл указан дважды, предложение уже отклонено или показанная версия файла устарела. Проверять это по одному неудобно. Новый endpoint собирает факты на сервере; ваша policy выносит понятный вердикт для каждого элемента.

Это **preflight**, то есть проверка перед действием. Он не одобряет предложения, не меняет файлы и не превращает несколько файлов в атомарную транзакцию. После `ready=true` пользователь по-прежнему принимает решения через обычный endpoint лекции. При применении сервер повторно проверяет актуальную версию файла.

## Что уже работает

В `homework` сохранены все возможности `lecture`: Chat/RAG/MCP, агентское чтение workspace, режимы `ASK`/`PLAN`/`EDIT`, предложения и ручное решение. Повторно писать эти части не нужно.

Предоставлены:

- `BatchRequest`: строгий JSON-декодер, принимающий только `proposalIds`.
- `BatchChecker`: загрузка предложений через `ControlledService`, текущих hash через `WorkspaceService` и времени через серверный `Clock`.
- `BatchInput` и `BatchReport`: неизменяемые входные данные и результат.
- `BatchController`, конфигурация и обработчик ошибок.
- Тесты предоставленного декодера и адаптеров.
- Восемь приёмочных тестов нового поведения.

**Единственная точка реализации:**

```text
src/main/java/dev/myfrei/repopilot/batch/ProposalBatchPolicy.java
```

Завершите `check(BatchInput input)`. В каркасе он явно бросает `UnsupportedOperationException`. Не переносите проверку в controller и не заменяйте серверные факты полями запроса.

## Контракт

Новый маршрут:

```http
POST /api/controlled/proposals/batch-check
Content-Type: application/json
```

```json
{
  "proposalIds": [
    "a4510882-8024-4eb7-a006-a0c5fe17aee2",
    "bd88ca82-2df8-40d8-aada-00c99190f884"
  ]
}
```

Используйте UUID реальных предложений своей сессии. Здесь приведены только примеры формы запроса.

Принимаются от 1 до 12 идентификаторов в канонической форме UUID. Повторять ID можно: это предмет проверки policy. Неизвестное предложение даёт HTTP 404, некорректный JSON — HTTP 400. Клиент не передаёт `path`, `status`, `currentHash`, время или признак разрешения.

Сервер собирает `BatchInput`:

```java
record BatchInput(Instant now, List<Item> items) {
    record Item(
        UUID id, String path, String mode, String status, boolean runActive,
        String baseHash, String currentHash, Instant expiresAt
    ) {}
}
```

`currentHash == null` означает, что получить текущую версию безопасным способом не удалось. Это не совпавшая версия и не разрешение на применение.

Результат:

```java
record BatchReport(List<Check> checks, boolean ready) {
    record Check(UUID id, String path, String status) {}
}
```

Для каждого входного элемента создайте ровно один `Check`. Сохраните порядок, идентификатор и путь; повторяющиеся элементы не удаляйте. Список результата не должен изменяться после возврата.

## Правила и приоритет

Проверки идут сверху вниз. Для элемента с несколькими проблемами возвращается только первый подходящий статус:

| Приоритет | Условие | Статус |
| --- | --- | --- |
| 1 | Его ID или путь встречается в пакете больше одного раза | `CONFLICTING_PATH` |
| 2 | `mode` не равен `EDIT` | `MODE_DENIED` |
| 3 | Сохранённый статус предложения не равен `PENDING` | `NOT_PENDING` |
| 4 | Исходный run ещё выполняется (`runActive`) | `RUN_ACTIVE` |
| 5 | `expiresAt` раньше `now` или совпадает с ним | `EXPIRED` |
| 6 | `currentHash` отсутствует | `UNAVAILABLE` |
| 7 | `currentHash` отличается от `baseHash` | `STALE` |
| 8 | Ни одно из условий выше не выполнено | `READY` |

Конфликт отмечается **у всех** участников, включая первое вхождение. Например, `A.java → B.java → A.java` даёт `CONFLICTING_PATH → READY → CONFLICTING_PATH`. Один ID с разными путями также конфликтует: даже если такой вход нельзя получить от обычного адаптера, чистая policy должна обрабатывать его однозначно.

`ready` равен `true`, только если каждый элемент имеет статус `READY`. Один плохой элемент не скрывает остальные результаты. Активный run получает `RUN_ACTIVE`, даже если срок уже истёк или hash недоступен: дождитесь завершения исследования. Policy не меняет статусы хранимых предложений, не вызывает `decide` и не обращается к файловой системе.

Пример: предложение одновременно `PLAN`, `REJECTED` и просрочено. Результат — `MODE_DENIED`. Предложение `EDIT/PENDING` с отсутствующим hash и уже истёкшим сроком получает `EXPIRED`.

## Шаги работы

1. Изучите `BatchInput` и тесты `ProposalBatchPolicyAcceptanceTest`.
2. Запустите базовые проверки. Они должны быть зелёными без реализации TODO.
3. Включите приёмочные тесты и убедитесь, что они падают из-за TODO.
4. Реализуйте чистую policy в указанном файле.
5. Проверьте смешанный пакет, а не только два корректных предложения.
6. Запустите полную проверку и заполните [SUBMISSION.md](SUBMISSION.md).

```bash
./mvnw test
./mvnw -Phomework -Dtest=ProposalBatchPolicyAcceptanceTest test
./mvnw -Phomework verify
```

Профиль `homework` включает приёмочные тесты новой policy. Без него исключён только `ProposalBatchPolicyAcceptanceTest`; существующие тесты и тесты адаптеров выполняются. До реализации policy приёмочные проверки выявляют TODO. Добейтесь их прохождения, не удаляя и не ослабляя условия.

Для проверки PostgreSQL требуется Docker:

```bash
./mvnw -Phomework,pgvector-it verify
```

Проверочные ответы модели задаются HTTP-фикстурами; локальная LLM не нужна для unit-тестов.

## Ручная проверка

Запускайте приложение только с учебным workspace, как описано в лекции. Для нового endpoint нужны те же три флага: `repopilot.agent.enabled`, `repopilot.workspace.enabled`, `repopilot.controlled.enabled`.

Создайте два предложения в режиме `EDIT`, сохраните их ID и отправьте пакет:

```bash
curl -sS http://localhost:8080/api/controlled/proposals/batch-check \
  -H 'Content-Type: application/json' \
  -d '{"proposalIds":["REPLACE_WITH_REAL_UUID_1","REPLACE_WITH_REAL_UUID_2"]}'
```

До реализации TODO endpoint отвечает HTTP 501 с кодом `BATCH_NOT_IMPLEMENTED`. После реализации корректный preflight возвращает HTTP 200; `ready=false` — штатный результат проверки, а не HTTP-ошибка.

Проверьте:

1. Два разных свежих `EDIT/PENDING` предложения → оба `READY`.
2. Один ID дважды → оба `CONFLICTING_PATH`.
3. Отклонённое предложение → `NOT_PENDING`.
4. После создания предложения вручную изменён файл → `STALE`.
5. После preflight повторно просмотрите diff и примите решение по одному предложению.

Сравните файлы до и после самого `batch-check`: байты не должны измениться. Не называйте `READY` подтверждением успешной компиляции: команды проверки появятся в уроке 5.7.

## Критерии приёмки

- Все восемь приёмочных тестов и базовые проверки проходят.
- Приоритеты, порядок и повторы соответствуют контракту.
- Нет чтения файлов, обращения к модели или выдачи разрешения внутри policy.
- Клиент не может подделать серверные hash, режим или срок.
- В отчёте показаны `READY`, конфликт, отказ и устаревшая версия.
- Объяснено, почему положительный preflight не заменяет проверку перед записью.

Необязательное усложнение: добавьте отдельное отображение результата пакета в UI. Оно должно вызывать готовый endpoint и не дублировать правила policy в JavaScript.
