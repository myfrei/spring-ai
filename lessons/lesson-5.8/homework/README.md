# Домашнее задание 5.8. План родительской перепроверки

[Материалы урока](../README.md) · [Лекция](../lecture/README.md) · [Приёмочные тесты](src/test/java/dev/myfrei/repopilot/researchplan/ResearchCheckPlanPolicyAcceptanceTest.java) · [Отчёт по ДЗ](SUBMISSION.md)

В [лекции](../lecture/README.md) изолированный исследователь возвращает findings с доказательствами чтения. Родитель должен проверить важные места самостоятельно. В этом задании вы добавляете **предпросмотр недостающих родительских чтений**.

Три findings могут перекрываться, ссылаться на одну версию файла или содержать уже прочитанные родителем строки. Простое «прочитать каждый диапазон заново» тратит бюджет. При этом нельзя считать чтение другого run доказательством родителя или тихо заменить устаревший hash текущей версией.

Новый endpoint строит точные диапазоны, которых ещё нет в родительском журнале. Он ничего не исполняет, не запускает второго субагента и не заменяет проверку результата из лекции.

## Предоставленная база

В `homework` полностью сохранены возможности `lecture`: один ограниченный read-only исследователь, общий бюджет, отмена, проверка происхождения findings и родительский gate.

Уже готовы:

- загрузка `ResearchRuntime.snapshot(parentRunId)`;
- выбор только принятых сервером child reports со статусом `CANDIDATE`;
- строгий разбор коррелированных успешных `readFile` из журнала родителя;
- получение текущих hash через `WorkspaceService`;
- DTO, decoder, controller, конфигурация, обработчик ошибок;
- три теста адаптеров и восемь приёмочных тестов.

Policy не получает statements, uncertainties, вопросы, свободные ответы, аргументы tools или содержимое файлов. Ей нужны только пути, версии и реально доставленные диапазоны строк.

Единственный TODO:

```text
src/main/java/dev/myfrei/repopilot/researchplan/ResearchCheckPlanPolicy.java
```

Реализуйте `check(ResearchCheckPlanInput input)`.

## Запрос

```http
POST /api/research/runs/{parentId}/read-plan
Content-Type: application/json
```

```json
{"readLineBudget":100}
```

Клиент передаёт только целый бюджет от 1 до 160 строк. Findings, родительские диапазоны и текущие hash загружаются сервером. Неизвестные поля, дробное число или нарушение границ дают HTTP 400. Неизвестный исследовательский запуск — HTTP 404.

Вход policy:

```java
record ResearchCheckPlanInput(
    UUID parentRunId,
    List<Finding> findings,
    List<ParentRead> parentReads,
    Map<String, String> currentHashes,
    int readLineBudget
) {
    record Finding(
        String path, String fullFileHash, int startLine, int endLine
    ) {}
    record ParentRead(
        UUID parentRunId, String path, String fullFileHash,
        int startLine, int endLine
    ) {}
}
```

Ограничения предоставленного DTO:

- findings: от 0 до 3; диапазон каждого — от 1 до 80 строк;
- parentReads: от 0 до 8; каждый — фактически возвращённые строки одного чтения;
- диапазоны включительные, номера от 1 до 100000;
- путь и hash проверены, hash — 64 строчные hex-цифры;
- не больше трёх текущих hash; отсутствие ключа означает недоступную версию;
- списки и map неизменяемы.

В родительские spans включаются только пары `function call → tool result` с одним ID и именем `readFile`, успешным закрытым envelope и проверенной формой `FileRead`. Непарные, неоднозначные или неуспешные ответы доказательством не являются. Полный журнал выбран потому, что отсутствие первого receipt и вытеснение ledger нельзя смешивать в одно утверждение «ничего не читалось».

Предпросмотр **не создаёт новый receipt**. Чтение метаданных журнала не равно доставке содержимого родительской модели. Штатный gate продолжает использовать свои правила; будущие запросы чтения должны пройти через обычный runtime.

## 1. Исключите неподходящие версии

Для каждого finding примените первый подходящий вариант:

| Приоритет | Условие | Статус |
| --- | --- | --- |
| 1 | В findings у этого пути встречается несколько разных hash | `VERSION_CONFLICT` |
| 2 | Текущий hash пути отсутствует | `UNAVAILABLE` |
| 3 | Текущий hash отличается от hash finding | `STALE` |
| 4 | Версия подходит; все строки уже прочитаны родителем | `ALREADY_READ` |
| 5 | Версия подходит; часть строк ещё не прочитана | `NEEDS_READ` |

При конфликте отметьте **все** findings этого пути, включая первое. Не выбирайте молча ту версию, которая совпала с текущей. Повтор одинакового hash конфликтом не является.

Для `VERSION_CONFLICT`, `UNAVAILABLE` и `STALE` не создавайте чтений; `missingLines=0` обозначает отсутствие допустимого расчёта, а не подтверждённое чтение. Весь план при таких findings не может быть `complete=true`.

Устаревший finding не превращается в задачу прочитать новую версию под старым hash. Сначала нужно получить актуальное исследовательское основание.

## 2. Вычтите доставленные родителю строки

Для подходящего finding учитывайте только spans с точным совпадением:

```text
parentRunId + path + fullFileHash
```

Чтения дочернего run, другой версии или другого пути не закрывают диапазон родителя.

Объедините пересекающиеся и соседние прочитанные интервалы. Затем вычтите их из диапазона finding. Дыры остаются дырами: чтения `1–5` и `8–10` не покрывают строки `6–7`.

`missingLines` в отчёте finding — число его непокрытых строк. Если результат равен нулю, статус `ALREADY_READ`; иначе `NEEDS_READ`.

Флаги `truncated` или `rangeComplete=false` в исходном результате не означают нулевое чтение: учитываются только фактически доставленные `startLine–endLine`. Данные за этим диапазоном не достраиваются.

## 3. Постройте общий набор недостающих диапазонов

Для каждого допустимого пути:

1. Объедините пересекающиеся и соседние диапазоны findings одной версии.
2. Вычтите объединённые подходящие parentReads.
3. Получите непересекающиеся интервалы недостающих строк.

Считайте строки общего набора один раз. Поэтому сумма `missingLines` отдельных перекрывающихся findings может быть больше общего `requiredLines`.

Порядок путей — первое появление **допустимого** finding во входном списке. Внутри пути диапазоны идут по возрастанию номера строки. Не сортируйте пути лексикографически и не закрывайте уже прочитанную дыру ради объединения двух задач.

Здесь «минимальный» означает отсутствие повторного запроса уже покрытых строк и двойного учёта перекрытий. Оптимизировать стоимость глобального поиска или читать известные строки ради уменьшения числа вызовов не требуется.

## 4. Разбейте на будущие чтения и примените бюджет

Каждый будущий `ReadTask` содержит не больше 80 строк. Проходите недостающие интервалы в определённом выше порядке и используйте доступный бюджет:

- максимум 80 строк на один task;
- максимум `readLineBudget` строк суммарно;
- последний task можно сократить до остатка бюджета;
- оставшиеся строки учитываются как отложенные.

Пример: после объединения нужно прочитать `1–240`, бюджет 100. План содержит `1–80` и `81–100`; 140 строк остаются отложенными. Это диапазоны будущих запросов, а не выдуманный частичный результат уже выполненного инструмента.

При границах входа число задач не превышает hard cap 16. Предоставленный DTO отчёта отклоняет превышение; молча обрезать список нельзя. Нарушение серверных границ даёт HTTP 409 с `READ_PLAN_EVIDENCE_LIMIT` или `READ_PLAN_TASK_LIMIT`, без частичного плана. Это защитная граница на случай будущего изменения контракта.

Бюджет задан в **запрошенных строках**. Даже task на 80 строк может вернуть меньше из-за byte/output caps обычного `readFile`. План не обещает успешного полного чтения: после реального выполнения runtime проверяет фактически доставленные строки заново. Возвращённый hash должен совпасть с `ReadTask.fullFileHash`; при изменении версии нужен новый план.

## Результат

```java
record ResearchCheckPlanReport(
    UUID parentRunId,
    List<FindingCheck> findings,
    List<ReadTask> reads,
    int requiredLines, int plannedLines, int deferredLines,
    boolean complete
) {
    record FindingCheck(
        int index, String path, String fullFileHash,
        int startLine, int endLine, String status, int missingLines
    ) {}
    record ReadTask(
        String path, String fullFileHash, int startLine, int endLine
    ) {}
}
```

- `findings` сохраняет исходный порядок и все исходные поля; `index` начинается с 0.
- `reads` содержит только допустимые версии и непокрытые строки, в порядке планирования.
- `requiredLines` — уникальные недостающие строки только допустимых findings.
- `plannedLines` — сумма длины созданных задач.
- `deferredLines = requiredLines - plannedLines`.
- `complete=true`, только если нет конфликтных/недоступных/устаревших findings и нет отложенных строк.
- Оба списка неизменяемы.

`complete` относится **к полноте плана**, а не к выполнению чтений, завершению исследования или правильности findings. При нуле принятых findings получается пустой полный план; это означает отсутствие известных задач чтения, а не достаточность исследования.

## Ручной сценарий

Запустите приложение с восемью флагами лекции: `agent`, `workspace`, `controlled`, `skills`, `plans`, `compaction`, `verification`, `research` через `repopilot.<имя>.enabled`. Получите исследовательский run с принятыми findings и просмотрите его snapshot:

```bash
curl -sS http://localhost:8080/api/research/runs/REPLACE_WITH_PARENT_RUN_UUID
```

Запросите предпросмотр:

```bash
curl -sS http://localhost:8080/api/research/runs/REPLACE_WITH_PARENT_RUN_UUID/read-plan \
  -H 'Content-Type: application/json' \
  -d '{"readLineBudget":100}'
```

До реализации TODO endpoint возвращает HTTP 501 с кодом `READ_PLAN_NOT_IMPLEMENTED`. После реализации корректный preview отвечает HTTP 200, включая неполный план или findings со статусом `STALE`.

Проверьте меньший бюджет, уже прочитанный диапазон и изменение файла после child report. Исходные parent messages, receipts, число tool executions и исследовательский snapshot после preview должны сохраниться. Новые range requests не выполняются автоматически.

## Приёмка

- Все восемь приёмочных тестов и базовые проверки проходят.
- Версии не смешиваются; конфликт, отсутствие файла и stale finding различимы.
- Чтения другого run/пути/hash не засчитываются.
- Перекрытия и смежные интервалы объединяются; непокрытые дыры сохраняются.
- Общая длина уникальна, задачи ограничены 80 строками и общим бюджетом.
- Последний task корректно использует оставшийся бюджет; отложенные строки подсчитаны.
- Нет исполнения, нового receipt или расширения прав.
- В [SUBMISSION.md](SUBMISSION.md) объяснено различие полного плана и выполненной проверки.

Необязательное усложнение: визуальный список будущих чтений с отдельным действием пользователя для обычного запуска. Предпросмотр не должен сам исполнять tasks.
