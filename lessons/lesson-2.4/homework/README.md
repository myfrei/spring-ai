# ДЗ 2.4. Парный отчёт регрессий

## Чем задача отличается от лекции

Лекция показывает сводные оценки по режимам. ДЗ сравнивает два прогона по одному caseId и repetition: рост среднего не должен скрыть ухудшение конкретного ответа или цитаты.

В homework **уже включено готовое базовое приложение lecture**. Реализовывать его заново или переносить ответы из лекции не требуется. Новый учебный код находится в `dev.myfrei.repopilot.homework`; незаполнен только метод нового класса `PairedRunComparator`. REST-включение и остальная инфраструктура предоставлены.

| --- | --- |
| Весь работающий срез лекции и его регрессионные тесты | Новую policy, которой в лекции нет |
| Новый API, DTO и вызов policy в продукте | Самостоятельный алгоритм по контракту ниже |
| 6 отдельных acceptance-проверок | Собственное объяснение выбранного поведения и его ограничений |


Каркас собирается. Базовые Java/JS-проверки должны быть зелёными; последние 6 acceptance сначала красные из-за явного TODO. После реализации запустите полный `./mvnw test` и `npm test`.

Не заменяйте тесты константами и не выключайте их. Проверено, что во временной копии с заменой **только одного нового policy-файла** неизменённые тесты проходят. Эталонного решения в homework нет.

## Контракт парного сравнения

Реализуйте `PairedRunComparator.compare(baseline, candidate, mode)`. Готовый controller читает сохранённые JSON через RunStore. Новый отчёт не вызывает модель и не меняет исходные прогоны.

1. RUNNING или отсутствие conditions — PAIR_RUN_NOT_READY. Split и полные Conditions должны совпадать; иначе PAIR_CONDITIONS_MISMATCH. Это сравнение одинаковых model/corpus/index/prompt/budget/pipeline. Request topK/threshold могут отличаться — именно их последствия можно исследовать.
2. Mode должен присутствовать в requests обоих прогонов.
3. Ключ строки: caseId + repetition, не ordinal и не позиция массива. Дубли ключа одного режима отклоняются.
4. Возьмите объединение ключей, сортируйте по caseId/repetition. Отсутствующая с одной стороны строка явно ONLY_BASELINE/ONLY_CANDIDATE; не скрывайте её пересечением.
5. Допустимые для ручного качества outcomes — COMPLETED/NO_EVIDENCE. Успех → FAILED/CANCELLED считается EXECUTION_REGRESSION, обратное — EXECUTION_RECOVERY. Два неуспешных — BOTH_UNSUCCESSFUL.
6. Для двух допустимых outcomes без хотя бы одного Judgment — UNASSESSED; отсутствующая оценка не равна нулю.
7. Иначе answerDelta/citationDelta = candidate − baseline. Любое отрицательное изменение означает regression. Улучшением называйте положительное изменение без регрессии на другой оси. Лучший ответ с худшими цитатами не становится однозначной победой.
8. totalMsDelta допустима только если обе строки COMPLETED. NO_EVIDENCE или ошибка не получают преимущество за отсутствие генерации.
9. Счётчики qualityCompared/regressions/improvements/unpaired/unassessed должны соответствовать строкам. Не выбирайте победителя автоматически.

## API и демонстрация

Сделайте два DEV-прогона штатной панелью 2.4, сохраните ручные оценки и подставьте реальные UUID:

```bash
curl -sS 'http://127.0.0.1:8080/api/evaluation/pairs?baseline=BASELINE_UUID&candidate=CANDIDATE_UUID&mode=RAG'
```

Оба прогона должны иметь ту же версию корпуса/dataset/model/index; для исследования topK/threshold меняйте их в Request, а не перестраивайте одновременно encoder. Сравнение разных моделей/системных инструкций требует отдельно спроектированных правил сопоставимости, здесь оно отклоняется.

Тест содержит важный контрпример: baseline scores [2,0], candidate [1,2]. Средняя оценка выросла, но dev-01 регрессировал. Ваш отчёт обязан показать обе строки и снижение на конкретном вопросе.

## Проверки и сдача

```bash
./mvnw verify -Ppgvector-it
```

Профиль требует Docker; само paired comparison работает по сохранённым файлам без inference. Сдайте policy и [SUBMISSION.md](SUBMISSION.md): два run ID, совместимость условий, парные изменения, ошибки/неоценённые/непарные случаи и решение, которое не скрывает ухудшений средним.

HOLDOUT не используйте для очередного выбора threshold. Для реальных выводов нужны настоящие модели и ручные оценки; синтетический acceptance — только проверка алгоритма.
