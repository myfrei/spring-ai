# Домашнее задание 5.5. Выбор следующих шагов плана

В [лекции](../lecture/README.md) RepoPilot хранит план, управляет состояниями шагов и проверяет доказательства завершения. В этом задании вы добавляете **предпросмотр очереди доступных шагов с приоритетами и бюджетом чтения**.

Пользователь видит четыре шага, но хочет отвести на следующую итерацию, например, не больше двух шагов и 30 строк кода. Какую работу показать первой? Уже активную, или ту, которая разблокирует больше обязательных задач? Что делать, если самая важная работа слишком велика?

Вы реализуете выбор. Новый endpoint не запускает инструменты, не меняет план и не обещает параллельное выполнение. Повторять агентский цикл, `startPlanStep`, `completePlanStep` или сброс зависимостей из лекции не нужно.

## Предоставленная база

Все возможности `lecture` сохранены в `homework`. Уже готовы:

- загрузка свежего `PlanSnapshot` через `PlanRuntime.snapshot(runId)`;
- серверные статусы, зависимости, диапазоны чтения и признаки актуальности evidence;
- строгий decoder запроса, DTO, controller, конфигурация и обработчик ошибок;
- три теста предоставленных адаптеров;
- восемь приёмочных тестов нового алгоритма.

Единственный TODO:

```text
src/main/java/dev/myfrei/repopilot/frontier/PlanFrontierPolicy.java
```

Реализуйте `check(FrontierInput input)`. Policy работает с готовыми фактами. Она не читает файлы, не обращается к LLM, не меняет evidence и не отмечает шаги завершёнными.

## Входные данные

```http
POST /api/plans/runs/{id}/frontier/check
Content-Type: application/json
```

```json
{"maxSteps":2,"readLineBudget":30}
```

`maxSteps` — целое число от 1 до 4; `readLineBudget` — от 1 до 160. Только эти два поля принадлежат клиенту. Статусы, граф зависимостей, версии файлов и признак актуальности загружаются сервером. Неизвестные поля, дроби, строки вместо чисел или выход за границы дают HTTP 400. Неизвестный запуск плана — HTTP 404.

Policy получает:

```java
record FrontierInput(
    UUID runId, int revision, List<Step> steps,
    int maxSteps, int readLineBudget
) {
    record Step(
        String id, String status, boolean evidenceCurrent,
        int startLine, int endLine,
        List<String> dependsOn, boolean required
    ) {}
}
```

В плане от одного до четырёх уникальных шагов. Зависимости указывают только на более ранние шаги. Циклы, неизвестные зависимости и дубликаты отклоняет готовый DTO. Списки неизменяемы.

Диапазон включительный. Стоимость шага в строках:

```text
lineCost = endLine - startLine + 1
```

Это **учебная оценка объёма следующего чтения**, а не число токенов, время работы или гарантия стоимости полного agent run. Стоимость каждого шага от 1 до 80 строк.

## 1. Определите доступность

Шаг `COMPLETED` не выбирается для перезапуска:

- актуальное evidence → статус `COMPLETED` в отчёте;
- устаревшее evidence → `STALE_COMPLETED`.

Вернуть такой шаг в работу можно через штатные действия лекции. Policy предпросмотра сама этого не делает.

Для шагов `PENDING` и `ACTIVE` проверьте **всех транзитивных предков**. Каждый должен быть `COMPLETED` с `evidenceCurrent=true`. Иначе статус шага — `BLOCKED_DEPENDENCY`.

Пример: `A → B → C`. У `B` собственный hash актуален, но у `A` evidence устарело. `C` всё равно заблокирован. Один текущий непосредственный предшественник не исправляет устаревшего предка.

У незавершённого шага `evidenceCurrent=false` само по себе нормально: доказательство ещё не получено. Это не блокирует независимый `PENDING` или `ACTIVE` шаг без предков.

## 2. Вычислите важность для графа

`criticality` — количество **уникальных обязательных транзитивных потомков** шага. Сам шаг в это число не входит. Флаг `required` самого кандидата не даёт отдельного приоритета.

Для цепочки `A → B → C`, где `B` и `C` обязательные, у `A` значение 2. Если обязательный потомок достижим двумя путями в ромбе, считать его нужно один раз. Состояние потомка не меняет этот структурный показатель: учитывайте все вершины с `required=true`.

Вычислите показатель для каждого шага, включая уже завершённые и заблокированные: это помогает объяснить результат пользователю.

## 3. Отсортируйте доступную работу

Для доступных `PENDING`/`ACTIVE` шагов порядок такой:

1. `ACTIVE` перед `PENDING`.
2. Большее `criticality` перед меньшим.
3. При равенстве — исходный порядок плана.

Не сортируйте по имени или размеру файла. Порядок графа в исходном плане не меняется: это только отдельная очередь выбора.

## 4. Распределите бюджет

Обходите доступные шаги в полученном порядке:

| Условие | Статус |
| --- | --- |
| Уже выбрано `maxSteps` шагов | `SELECTION_LIMIT` |
| `lineCost` больше оставшегося бюджета | `OVER_BUDGET` |
| Иначе | `SELECTED` |

Только `SELECTED` расходует строки и количество мест. Большой неподходящий шаг не останавливает обход: более маленький следующий ещё может поместиться. Если лимит количества уже достигнут, `SELECTION_LIMIT` имеет приоритет над недостатком строк.

Это определённый контрактом жадный выбор с приоритетами. Искать оптимальный набор с максимальной суммой важности не требуется.

Пример: бюджет 3 строки, лимит 4 шага. Активному шагу нужно 80 строк, следующим ожидающим — 1, 2 и 1. Получится `OVER_BUDGET → SELECTED → SELECTED → OVER_BUDGET`; расход ровно 3 строки.

## Формат результата

```java
record FrontierReport(
    UUID runId, int revision, List<Check> checks,
    List<String> selectedStepIds, int usedLines, int remainingLines
) {
    record Check(
        String stepId, String originalStatus, String status,
        int criticality, int lineCost
    ) {}
}
```

- `checks`: ровно один результат на шаг, **в исходном порядке плана**.
- `selectedStepIds`: только выбранные шаги, **в порядке ранжирования**.
- `usedLines`: сумма стоимости выбранных шагов.
- `remainingLines`: исходный бюджет минус расход; значение неотрицательное.
- `runId`, `revision`, `stepId` и `originalStatus` сохраняются.
- Списки результата неизменяемы.

## Ручная проверка

Запустите приложение как в лекции: включите `repopilot.agent.enabled`, `workspace.enabled`, `controlled.enabled`, `skills.enabled`, `plans.enabled` с префиксом `repopilot` у каждого свойства. Получите реальный `runId` сценария с планом. Для демонстрации выбора нужен снимок с незавершёнными шагами; для полностью завершённого плана пустой выбор корректен.

```bash
curl -sS http://localhost:8080/api/plans/runs/REPLACE_WITH_RUN_UUID/frontier/check \
  -H 'Content-Type: application/json' \
  -d '{"maxSteps":2,"readLineBudget":30}'
```

До реализации TODO endpoint отвечает HTTP 501 с кодом `FRONTIER_NOT_IMPLEMENTED`. После реализации корректный предпросмотр возвращает HTTP 200, даже если все шаги заблокированы или не помещаются.

Сравните обычный снимок плана до и после запроса: revision и статусы должны сохраниться. Проверьте меньший бюджет, лимит одного шага и устаревшее evidence завершённого предка. Не редактируйте серверные факты через JSON запроса.

## Приёмка

- Восемь приёмочных тестов и базовые проверки зелёные.
- Учитываются транзитивные предки и уникальные обязательные потомки.
- Активный шаг имеет приоритет; равенство сохраняет порядок плана.
- Большой шаг пропускается без потери возможности выбрать последующий маленький.
- Выполняются обе границы бюджета и правильный приоритет причин отказа.
- Ни одна проверка не меняет план или права агента.
- В [SUBMISSION.md](SUBMISSION.md) показаны порядок выбора, расход строк и один заблокированный сценарий.

Необязательное усложнение: UI предпросмотра очереди. Он отображает решение сервера и не запускает шаги автоматически.
