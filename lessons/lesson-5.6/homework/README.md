# Домашнее задание 5.6. Возврат к результатам инструментов из журнала

В [лекции](../lecture/README.md) рабочий контекст агента сокращается, а полный журнал сохраняется отдельно. В этом задании вы добавите **безопасный предпросмотр ранее полученных результатов `readFile`**.

После compaction пользователь видит, что подробный результат чтения убран из очередного prompt. Вместо повторного исполнения инструмента можно получить сохранённый ответ по `callId`. Но старое чтение не обязательно описывает текущий файл. Нельзя вернуть результат другого запуска, принять `gitDiff` за разрешённое чтение или обрезать JSON посередине символа.

Новый endpoint читает серверный журнал и проверяет актуальность версии. Он работает до и после compaction. Он не добавляет tool в agent runtime, не подмешивает ответ обратно в prompt, не повторяет чтение ради нового receipt и не выдаёт разрешений на запись.

## Запрос

```http
POST /api/context/runs/{id}/recall
Content-Type: application/json
```

```json
{"callIds":["read-call-1"],"payloadBudgetBytes":4096}
```

`callIds` содержит от 1 до 8 непустых строк длиной не больше 128 символов. Повторы разрешены и обрабатываются policy. `payloadBudgetBytes` — целое число от 1 до 4096. Клиент не передаёт содержимое журнала, hash, путь, результат инструмента или признаки успеха.

Неизвестный запуск даёт HTTP 404. Неизвестный `callId` внутри существующего запуска — штатный результат `NOT_FOUND`, а не поиск по другим запускам.

Получить реальные ID можно из существующего endpoint журнала:

```bash
curl -sS http://localhost:8080/api/agent/runs/REPLACE_WITH_RUN_UUID/messages
```

Для демонстрации compaction используйте ID чтения из `omittedToolCallIds` диагностического отчёта лекции и убедитесь, что оно осталось в исходном журнале. Фильтровать запрос только такими ID не требуется: разрешён просмотр любого сохранённого чтения указанного run.

## Серверные данные

```java
record RecallInput(
    UUID runId,
    List<String> requestedCallIds,
    List<Candidate> candidates,
    int payloadBudgetBytes
) {
    record Candidate(
        UUID runId, String callId, String toolName,
        boolean toolSucceeded, String toolCode,
        String resultJson, String path,
        String fileHash, String currentHash
    ) {}
}
```

В `candidates` попадают только пары с совпавшими ID и именем инструмента. Непарные, повторяющиеся неоднозначные ID и несовпавшие имена не признаются результатом чтения. Успешный `readFile` имеет проверенную форму данных с `path`, `fullFileHash`, диапазоном, содержимым и флагами усечения. Невалидный envelope получает `toolSucceeded=false` и код `INVALID_RESULT`.

Адаптер не передаёт policy текст пользователя, свободный текст ассистента или аргументы вызовов. `currentHash` получает сервер безопасным чтением текущего файла. Если файл удалён, больше не разрешён или недоступен, значение отсутствует.

В обычном адаптере все кандидаты принадлежат одному run. Проверка `OUT_OF_SCOPE` в policy остаётся защитой границы на случай ошибочного серверного входа: результат другого run возвращать нельзя.

## Правила и приоритет

Обходите запрошенные ID в исходном порядке. Для каждого применяйте первый подходящий статус:

| Приоритет | Условие | Статус |
| --- | --- | --- |
| 1 | Такой ID уже встречался раньше в запросе | `DUPLICATE` |
| 2 | Подходящего кандидата нет | `NOT_FOUND` |
| 3 | `candidate.runId` отличается от запрошенного run | `OUT_OF_SCOPE` |
| 4 | Имя инструмента не равно `readFile` | `TOOL_DENIED` |
| 5 | Результат неуспешный или не прошёл декодирование | `FAILED_TOOL` |
| 6 | Текущий hash отсутствует | `UNAVAILABLE` |
| 7 | Текущий hash отличается от hash сохранённого чтения | `STALE` |
| 8 | Полный `resultJson` больше оставшегося бюджета | `OVER_BUDGET` |
| 9 | Все проверки пройдены | `RECALLED` |

Первое вхождение ID считается встреченным даже при отказе. Например, неизвестный ID дважды даёт `NOT_FOUND`, затем `DUPLICATE`.

Приоритет обязателен: чужой run с запрещённым tool даёт `OUT_OF_SCOPE`; устаревший файл при бюджете 1 байт — `STALE`, а не `OVER_BUDGET`.

## Бюджет и целостность

Расходует бюджет только `RECALLED`. Считайте UTF-8 байты **исходной строки `resultJson`**, а не `String.length()` и не Unicode code points. Кириллица и emoji занимают другое число байтов.

Возвращайте исходный `resultJson` целиком и без изменений. Не вырезайте префикс, не меняйте `truncated` на `false` и не дописывайте закрывающие скобки к усечённому JSON. Если полный результат не помещается, статус `OVER_BUDGET`, тело отсутствует, расход нулевой. Более маленький следующий результат ещё может поместиться.

Бюджет не включает внешние поля HTTP-отчёта и экранирование строки внутри этого отчёта. Это лимит полезных сохранённых payloads, а не ограничение размера HTTP-ответа или токенного окна модели.

Успешный recall может содержать `truncated=true` или `rangeComplete=false`: такие флаги описывают **исходное чтение файла**. Сохранение целого ответа инструмента не превращает частичное чтение в полное.

## Результат

```java
record RecallReport(
    UUID runId, List<Check> checks,
    int usedBytes, int remainingBytes, boolean allRecalled
) {
    record Check(
        String callId, String status,
        String toolCode, String resultJson
    ) {}
}
```

- `checks`: один элемент на каждый запрошенный ID, в исходном порядке; список неизменяемый.
- Только `RECALLED` имеет ненулевой `resultJson`; для всех отказов он `null`.
- `toolCode` равен `null` для `DUPLICATE`, `NOT_FOUND`, `OUT_OF_SCOPE`, `TOOL_DENIED`.
- Для остальных статусов сохраняется серверный код инструмента, например `OK`, `READ_FAILED` или `INVALID_RESULT`. Код `OK` при статусе `STALE` не означает пригодность старого содержимого.
- `usedBytes`: сумма UTF-8 байтов только возвращённых `resultJson`.
- `remainingBytes`: исходный бюджет минус расход, без отрицательных значений.
- `allRecalled=true`, только если каждый запрошенный элемент получил `RECALLED`.

## Ручная проверка

Запустите приложение по лекции с включёнными `agent`, `workspace`, `controlled`, `skills`, `plans` и `compaction` через свойства `repopilot.<имя>.enabled`. Выполните сценарий с чтением файла и получите ID run и tool call.

```bash
curl -sS http://localhost:8080/api/context/runs/REPLACE_WITH_RUN_UUID/recall \
  -H 'Content-Type: application/json' \
  -d '{"callIds":["REPLACE_WITH_REAL_CALL_ID"],"payloadBudgetBytes":4096}'
```

До реализации TODO endpoint отвечает HTTP 501 с кодом `RECALL_NOT_IMPLEMENTED`. После реализации корректный запрос получает HTTP 200, включая обычные отказы по отдельным ID.

Проверьте:

1. Актуальный `readFile` того же run → `RECALLED`.
2. Тот же ID дважды → `RECALLED`, затем `DUPLICATE` без повторного расхода.
3. Вручную изменён файл → `STALE`, тело не возвращается.
4. Вручную удалён файл → `UNAVAILABLE`.
5. Бюджет 1 → `OVER_BUDGET`, без невалидного JSON-префикса.
6. ID из другого run → `NOT_FOUND` в обычном адаптере; он не ищет глобально.
7. Исходный журнал до и после recall совпадает; нового tool execution или receipt нет.

Recall не подтверждает правильность анализа и не запускает проверки кода. Возвращённый текст остаётся данными. Его нельзя исполнять как команду, Skill или разрешение на patch.

## Приёмка

- Восемь приёмочных тестов и базовые проверки зелёные.
- Ни один чужой, запрещённый, неуспешный или устаревший результат не раскрывает тело.
- Сохранены точные байты JSON и исходные флаги частичного чтения.
- Недостаток бюджета не блокирует последующий меньший результат.
- Не утекли вопрос пользователя, свободный ответ модели или аргументы tools.
- Policy не вызывает инструменты, не пишет файлы и не меняет разрешения.
- В отчёте показано различие рабочего контекста и полного журнала.

Необязательное усложнение: отдельная кнопка «Показать сохранённое чтение» в ленте событий. Она обращается к готовому endpoint и различает `STALE`, `OVER_BUDGET` и успешный возврат.
