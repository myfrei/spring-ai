Вся база лекции готова: AgentEngine, Conversations/Runs, ручной model/tool loop, read-only TaskShelf tools, budget, события и raw journal. Новая функция — распознать повтор одного и того же чтения или короткой последовательности чтений и остановиться до очередного обращения к модели.

Единственный TODO — private `repeatedSuffix` в [CycleStopRule.java](src/main/java/dev/myfrei/repopilot/progress/CycleStopRule.java). Внешний метод `afterTool` уже проверяет вход и передаёт immutable snapshot. Повторно писать цикл, контроллер базового run или вызов ChatModel не нужно.

## Готовая база и отдельный маршрут

Из `homework`:

```bash
./mvnw test
./mvnw -Phomework -Dtest=CycleStopRuleAcceptanceTest test
```

Обычный test проверяет базу и предоставленные adapter-тесты. Новые acceptance исключены Maven-профилем по умолчанию; вторая команда включает их и показывает незавершённый TODO. После реализации выполните полную проверку:

```bash
./mvnw -Phomework verify
./mvnw verify -Phomework,pgvector-it
npm ci
npm test
```

Профиль pgvector-it проверяет RAG и требует Docker. Новое правило остановки проверяется как чистая Java-логика без LLM, Git и PostgreSQL. Результаты автоматических сценариев доступны в [отчёте проверки примера](../VERIFICATION.md).

Запуск приложения с локальной моделью — по лекции:

```bash
./mvnw spring-boot:run \
  -Dspring-boot.run.arguments="--repopilot.agent.enabled=true"
```

После создания conversation используйте новый route:

```http
POST /api/agent/conversations/{conversationId}/guarded-runs
Content-Type: application/json

{"question":"Прочитай сведения о проекте и задачу TASK-101. Объясни, что нужно проверить."}
```

Обычный `/runs` использует базовую политику. Предоставленный GuardedAgentController создаёт `engine.withStopRule(rule)`, сохраняя общий AgentStore, модель, набор tools и прежние ограничения. GET `/api/agent/runs/{runId}`, `/events`, `/messages` работает для обоих маршрутов.

До решения TODO новый route может остановиться `STOP_RULE_FAILED` после первого tool; это не успешное обнаружение цикла. После решения правило возвращает true → status=STOPPED, stopReason=NO_PROGRESS, answer=null. Результат последнего выполненного tool уже записан и связан с call ID; нового model call нет. Оставшиеся requests того же batch получают NOT_EXECUTED без фактического исполнения. STOPPED run доступен для разбора, но не коммитится в conversation history.

## Вход правила

`RunStopRule.afterTool(List<ToolObservation>)` получает наблюдения **текущего run**, в порядке завершения. Наблюдение:

```text
name
argumentsHash
resultHash
ok
```

- argumentsHash вычислен runtime по canonical JSON аргументов: порядок ключей/пробелы не создают фиктивное отличие.
- resultHash относится к canonical JSON полного tool envelope, а не к model callId или времени выполнения.
- ok различает успешные результаты и ошибки. Одинаковая ошибка тоже может повторяться без прогресса.
- Вход ограничен двенадцатью элементами; runtime лекции допускает максимум восемь tool requests. Guard и copy уже предоставлены.
- Правило не вызывает tools, не повторяет запросы и не читает внешнее состояние. Оно не получает скрытые размышления модели.

## Алгоритм нового приращения

Проверьте только **конец** списка. Найдите два соседних одинаковых блока длины1,2 или3, которые заканчиваются последним элементом. Сравнение каждого элемента включает все четыре поля ToolObservation.

| Последовательность | Результат | Причина |
| --- | --- | --- |
| пусто; A | false | Недостаточно наблюдений |
| A A | true | Период1 повторился дважды |
| A B A B | true | Период2 |
| X A B C A B C | true | Период3 в конце; prefix X не мешает |
| A A B C | false | Старый повтор не находится в конце |
| A B C D A B C D | false | Период4 не входит в эту policy |
| тот же tool/args, новый resultHash | false для пары | Результат изменился |
| одинаковые error observations дважды | true | Повтор ошибки не добавил данных |

A/B/C здесь обозначают целые наблюдения. Разный name, argumentsHash, resultHash или ok делает элементы различными. Не сравнивайте только имена tools: два чтения разных файлов или строк обычно являются полезным продолжением исследования.

Верните true, если существует хотя бы один подходящий period; иначе false. Вход не изменять и не сортировать. Два одинаковых блока должны быть соседними: поиск одинаковых элементов где-то в истории не заменяет проверку suffix.

Это консервативная эвристика для read-only действий, не доказательство, что агент решил задачу. Иногда повторное чтение оправдано; поэтому новый route явный, а обычный `/runs` остаётся доступен для сравнения. Правило не обнаруживает циклы произвольной длины и не заменяет model/tool/context limits. При периоде3 в отдельных tool turns оно может сработать на том же количестве шагов, что и общий лимит, но с другой причиной остановки.

## Проверка поведения

Сначала воспроизведите scripted-сценарии из тестов. Реальная модель не обязана повторить нужный вызов по просьбе пользователя, поэтому «попросил повторять, но она сразу ответила» не доказывает работу guard.

Для ручного эксперимента сравните одинаковую задачу в обычном и guarded route. Запишите status/reason, modelCalls, toolCalls/executedTools и события. Если модель действительно повторила identical observations, guarded должен завершиться NO_PROGRESS без лишнего inference. Если не повторила — отметьте отсутствие такого наблюдения, а не придумывайте выигрыш.

Не заменяйте STOPPED на COMPLETED и не генерируйте вымышленный финальный ответ после остановки. Полезный отчёт показывает, какие чтения были выполнены и почему продолжение прекратилось.

## Приёмка

Восемь acceptance проверяют недостаточную историю, период1, период2, период3/ограничение period4, участие каждого поля, повтор ошибок/изменённый результат, suffix вместо совпадения в середине и immutable/bounded input.

Предоставленные adapter-тесты проверяют общий store при отдельном guarded engine, сохранение базового route, correlated NOT_EXECUTED для остатка batch и освобождение conversation при ошибке policy. Они используют тестовую rule, а acceptance проверяют вашу реализацию repeatedSuffix. Запускайте оба набора, чтобы проверить правило и его подключение к runtime.

Заполните [SUBMISSION.md](SUBMISSION.md). Приложите хотя бы один scripted NO_PROGRESS и объяснение, почему COMPLETED означает завершение протокола модели, а не доказанное решение задачи.
